# 架构决策记录（ADR）

> 记录「为什么」，不重复「是什么」——机制与用法归 CLAUDE.md / docs/EXTENSION_POINTS.md /
> docs/PERSISTENCE_LANES.md，本目录只收难以从代码反推的决策及其取舍。
> 本仓是多会话 AI 并行开发形态：执行器只看任务书，重大「为什么」若无处可查，
> 每个新会话都要全仓 grep 考古，且易误判。

## 什么时候写

- 做了**不可逆或改回来很贵**的选择（存储选型、分层规则、对外契约语义）；
- 评审中有明确的「做/不做」结论且理由不在代码行为里（如「为什么 X 不自动清理」）；
- 同类问题容易被反复重新提出、且答案反直觉（不写就会有人再提一次）。

不写：实现细节、可从代码直接读出的行为、单一提案内的小取舍（写进提案台账即可）。

## 轻量模板（一篇 ≤60 行）

```markdown
# ADR-NNN <标题>

- 状态：已采纳（| 已被 ADR-MMM 取代）　日期：YYYY-MM-DD

## 背景
（面临什么问题/约束，为什么当时要决策。引现有代码/文档锚点。）

## 决策
（选了什么。给一句可直接被引用的结论。）

## 后果
（正面收益；接受的负面与边界；后续遇到什么情况需要重新评估。）

## 关联
（提案号 P-xxxx、合入提交、相关文档与代码锚点。）
```

## 流程约定

1. **先查后定**：动架构面（持久化/分层/契约语义）前先翻本目录，避免重新发明已被否决的方案；
2. **落新决策补一篇**：增强提案或手工提交引入上述「什么时候写」的决策时，同 PR 补 ADR
   （编号递增，文件名 `adr-NNN-<kebab-title>.md`），并在下方索引登记一行；
3. **决策被推翻时**：不删除旧篇——改状态为「已被 ADR-MMM 取代」，另起新篇；
4. ADR 是文档不是规范：与代码实况冲突时以代码为准，并按 docs-follow-code 纪律回填修订本篇。
