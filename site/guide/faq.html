Ports & access端口与访问

Port 9999 is taken — or the service won't bind端口 9999 被占——或者服务起不来绑定失败

Find the holder, free the port or pick another one: 先找占用方，然后腾出端口或换一个：

netstat -ano | findstr :9999# Windows — find the holder PID
lsof -i:9999# macOS / Linux（或 ss -tlnp sport = :9999）

The holder may be another Codecombo instance — codecombo stop -p 9999 stops it precisely. On Windows, a bind refusal can also mean a reserved port range (netsh interface ipv4 show excludedportrange protocol=tcp). Pick another port with CODECOMBO_PORT at install time or server.httpPort in config.json afterwards — startup logs print an actionable hint on every bind failure. 占用方可能就是另一套 Codecombo 实例——codecombo stop -p 9999 可精确停掉它。Windows 上绑定被拒还可能是保留端口段 （netsh interface ipv4 show excludedportrange protocol=tcp）。安装时用 CODECOMBO_PORT、装好后改 config.json 的 server.httpPort 换端口——每次绑定失败，启动日志都会给出可行动的定位提示。

Why are there extra ports next to the main one?主端口旁边怎么还有几个端口？

Three auxiliary ports sit next to the main one, each re-pointable in config.json (server.loopbackPort / sharePort / httpPort): 主端口旁固定有三个辅助端口，均可在 config.json 改道 （server.loopbackPort / sharePort / httpPort）：

  • main+1 loopback helper — local auxiliary channel (TLS deployments reach the plaintext API here on localhost). 主+1 回环辅助口——本机辅助通道（TLS 部署时本机明文 API 走这里）。
  • main+2 share sub-service — serves share links when they point at the share port directly. 主+2 分享子服务——分享链接直指分享口时由它服务。
  • main+3 plaintext companion — exists only while TLS is on, for networks where TLS-inspection appliances slow https to a crawl. It carries credentials in cleartext — trusted LANs only; set httpPort: 0 to turn it off. 主+3 明文伴随口——仅在 TLS 开启时存在，供深度检测网络里 https 被拖慢的场景。该端口凭据明文传输——仅限受信任内网；配 httpPort: 0 可显式关闭。
How do I open it to my phone or another machine?怎么让手机或其他机器访问？
codecombo start -H 0.0.0.0# bind all interfaces (default is 127.0.0.1 only)# 绑定所有网卡（默认只绑 127.0.0.1）

Then open http://<machine-ip>:9999 from the other device. The lock password (first-start setup) is the gate — bind to 0.0.0.0 only on networks you trust. For access from anywhere, the product ships an SSH reverse-tunnel mode through your own VPS — see the deployment docs. 然后在其他设备打开 http://<机器IP>:9999。 锁密码（首启设置）就是门——只在受信任的网络里绑 0.0.0.0。 任意网络随时访问可用自带 VPS 中继的 SSH 反向隧道模式——见部署文档。

Data & backups数据与备份

Where does Codecombo keep its data?Codecombo 的数据存在哪里？

One data directory, default ~/.codecombo — configuration, projects registry, keys, logs, everything. Installs that predate the rename (~/.simple-coding) are migrated automatically on first start of a new version — no manual move, don't pre-rename it yourself. 单一数据目录，默认 ~/.codecombo——配置、项目注册表、 密钥、日志都在里面。旧目录名（~/.simple-coding）的存量安装会在新版首次 启动时自动迁移——无需手动搬，也不要自己提前改名。

Custom location: pass CODECOMBO_DATA_DIR at install time (or --data-dir on manual starts). Re-running the installer must pass the same value back — omitting it rewrites the service unit without the variable, and the next restart reads the default directory instead (your data stays where it was; the instance just isn't looking at it). 自定义位置：安装时传 CODECOMBO_DATA_DIR（手动启动用 --data-dir）。重跑安装脚本必须把同一个值带回——漏带会重写出不含该 变量的服务单元，下次重启读到的是默认目录（数据仍在原地，只是实例不再读它）。

Where are layout and panel states kept? Do they survive a new browser or a new device?布局和面板状态存在哪里？换浏览器/换设备会保留吗？

Most of it lives server-side, tied to the instance, inside the data directory: panel sizes and open/closed state, open editor tabs, which main view was last up (notes / dsh console / share manager / remote console), pinned tree folders, rail order. Open the same instance from a different browser and it all comes back — the record belongs to the instance, not to your browser profile. Multiple instances (several installs on one machine, remote instances) each keep their own record. 绝大多数布局与面板状态按实例存服务端数据目录：面板尺寸与开合、 编辑器打开的标签、上次的主区视图（笔记 / dsh 控制台 / 分享管理 / 远程控制台）、文件树 钉选、活动栏顺序。换一个浏览器打开同一实例照样恢复——记录属于实例，不属于浏览器 profile。多实例（一台机器装多套、远程实例）各有独立记录，互不串扰。

Changing devices carries it along the same way backups do: the records sit in the data directory, so copying/moving that directory moves them (see the entries above). 换设备时这部分随数据目录走：记录就存放在数据目录里，整目录拷走/迁移 即一并带走（见上两条）。

A few items are deliberately browser-local (localStorage): the resizable inner sidebar widths of the terminal-session / remote / notes managers, floating terminal geometry, dismissed one-time hints, form drafts, the “Visual effects: reduced” tier (it describes this machine’s remote-control/GPU situation, not your account). Those do not follow you to another browser or device — each browser keeps its own copy. 少数项刻意存浏览器本地（localStorage）：终端会话管理 / 远程管理 / 笔记管理页的内嵌侧栏宽、终端悬浮窗几何、一次性提示已阅、表单草稿、视觉特效「减弱」档 （它描述的是本机的远控/GPU 形态，不是账号偏好）。这些不跨浏览器、 不跨设备跟随——每个浏览器各存一份。

How do I back it up?怎么备份？

Stop the service, copy the whole data directory, start it again — that's the whole recipe. 停服务 → 整目录拷走 → 再启动——全部步骤就这些。

One thing to know: SSH keys and API tokens are AES-256-GCM encrypted at rest, but the master key sits in the same directory by design (portability) — anyone holding the directory holds the secrets. Treat backups like your ~/.ssh folder: this encryption defends against single-file leakage, not a local attacker. 一点须知：SSH 私钥与 API 令牌落盘为 AES-256-GCM 加密，但主密钥按 可移植性设计就放在同一目录——拿到目录即拿到密钥。备份请按 ~/.ssh 的待遇 保管：这层加密防的是单文件泄露，防不了本机攻击者。

Startup logs DATA DIR NOT WRITABLE — or password setup fails with permission denied启动日志出现 DATA DIR NOT WRITABLE——或设密报 permission denied

The data directory isn't writable by the service — ownership, sandbox or SELinux. First check ownership; on SELinux systems (RHEL family) a systemd service domain cannot write home directories even with correct owners — the deployment guide has two equivalent fixes (a minimal audit2allow whitelist, or moving the data directory to /var/lib/codecombo). 服务写不了数据目录——属主、沙箱或 SELinux。先查属主；SELinux 系统 （RHEL 系）的服务域即使属主全对也写不了家目录——部署指南给了两个等价解法 （audit2allow 最小白名单，或把数据目录挪到 /var/lib/codecombo）。

Remote deployments handle this automatically (the SELinux whitelist module is installed for you when denials are detected). 远程部署会自动处理（检测到拒绝记录时自动生成并安装 SELinux 白名单 模块）。

Upgrading: which path is mine?升级：我该走哪条路？

The install method decides the update method. Identify your install first — systemctl cat codecombo and read the binary path in ExecStart (no unit, e.g. a manually started instance: ps -ef | grep codecombo shows the running path). 装法决定更法。先判别安装方式——systemctl cat codecombo 看 ExecStart 里的二进制路径（没有 unit 的形态，如手动启动的实例： ps -ef | grep codecombo 看运行中的路径）。

Two known shapes: during the beta phase the GitHub stable channel is empty — turn on Follow pre-releases in the version panel (Settings → About) before checking. And versions older than v0.0.1-beta.3 have a check-chain defect and can't see new releases in-app — upgrade once via the script or a manual replacement first, after that in-app checking works. 两种已知形态：beta 期 GitHub 正式通道恒为空——先在版本面板 （设置 → 关于）打开「跟进预发布版本」再检查；v0.0.1-beta.3 之前的 版本检查链有缺陷、应用内看不到新版本——先走脚本或手工换包升一次，之后应用内检查 即可用。

Manually replaced the binary on macOS? Don't use browser downloadsmacOS 手工换过二进制？别用浏览器下载产物

A release artifact downloaded in a browser carries the com.apple.quarantine attribute — background spawn may be silently refused, so an instance whose binary was replaced that way cannot start its in-app update's swap subprocess and the update dies without a visible error (the app just never comes back). Download binaries with curl, or clear the attribute with xattr -d com.apple.quarantine <binary>; an instance already stuck there upgrades once via the paths in the table above (script installs may re-run the install script; remote-deployed instances must never re-run it). If the attribute was already cleared and the symptom is unchanged, this is not the cause — see the launchd process-group case below. 浏览器下载的发布产物带 com.apple.quarantine 隔离 属性——后台 spawn 可能被静默拒绝，手工这样换过二进制的实例起不来应用内更新的 换包子进程，更新无声卡死（应用不再回来、也不报错）。二进制用 curl 下载，或用 xattr -d com.apple.quarantine <二进制> 清除属性； 已卡在该状态的实例先按上方判别表的路径升一次（脚本装可重跑安装脚本；远程部署装 禁止重跑）。若隔离属性已清而症状不变，则非此因——见下方 launchd 进程组案。

macOS: in-app update never completes — which case is it?macOS 应用内更新永远完不成——是哪一种？

launchd installs on v0.0.1-beta.9 or older: launchd cleans up the job's whole process group when the main process exits, so the update's swap subprocess is killed before it can even open its log — the app silently stays on the old version (no error, no result file, logs/update.log never created). From v0.0.1-beta.10 on, in-app update works. The plist side of the fix does not depend on the binary: re-running the install script writes AbandonProcessGroup=true and reloads the agent, so a script-installed ≤beta.9 instance upgrades in-app right after the re-run; remote-deployed instances get the key from a fresh remote deploy (central instance on beta.10+); otherwise install beta.10+ by hand. Tell the three silent-failure shapes apart: (1) the service log has start update process failed → the subprocess cannot start (quarantine/permissions); (2) no such line, logs/update.log does not exist and tmp/update-* holds a complete downloaded artifact → launchd process-group kill; (3) update.log contains waiting for old process → the liveness/wait chain stalled. Self-built systemd units must keep KillMode=process — the systemd default cleans up the swap subprocess the same way. All paths are relative to the data directory (the CC_DATA_DIR the service was started with; the product default otherwise). launchd 安装且版本 ≤ v0.0.1-beta.9：launchd 在 job 主进程退出时清理整个进程组，换包子进程连日志都来不及打开就被杀——应用静默 停在旧版本（不报错、无结果文件、logs/update.log 从不创建）。 从 v0.0.1-beta.10 起应用内更新可用。plist 侧修复与二进制无关：重跑 一键脚本会写入 AbandonProcessGroup=true 并重载代理，≤beta.9 的 脚本装实例重跑后即可正常应用内升级；远程部署实例由中心实例重新远程部署写回 （中心实例须 beta.10+）；否则手工装 beta.10+。三种静默失败判别式：（1）服务 日志有 start update process failed → 子进程起不来 （quarantine/权限）；（2）无该行、logs/update.log 不存在且 tmp/update-* 有完整下载产物 → launchd 组杀；（3） update.log 有 waiting for old process → 活性/等待链问题。自建 systemd unit 必须保留 KillMode=process ——systemd 默认同样会清理换包子进程。以上路径均相对数据目录（服务启动时的 CC_DATA_DIR，未显式指定时为产品默认目录）。

Why must remote-deployed instances never re-run the install script?为什么远程部署装的实例禁止重跑安装脚本？

The script's templated unit overwrites the deployer's unit: it drops the extra Environment=PATH (agent CLIs installed in the service user's environment then report “not found”), WorkingDirectory and NoNewPrivileges, and reverts the bind address to 127.0.0.1 — remote access dies at the next restart. The binary also ends up installed twice. That layout upgrades in-app, or via a fresh remote deploy, or by the manual replacement recipe (unit untouched). 脚本模板会覆写部署器写的 unit：丢掉多下发的 Environment=PATH（服务用户环境里装的智能体 CLI 随即 not found）、 WorkingDirectory 与 NoNewPrivileges，绑定地址缩回 127.0.0.1——下一次重启远程访问即断；二进制还会并存两份。该布局的升级走 应用内自更新、或中心实例重新远程部署、或 unit 原样不动的手工换包配方。

The update finished but the service didn't come back更新完成后服务没自己回来
sudo systemctl restart codecombo# script-installed (systemd) instances: finish the rollout# 脚本装（systemd 托管）实例：收尾拉起

Current install.sh registers a polkit rule so the app can restart its own service; instances installed by older scripts never got that rule and get refused — re-running the install script once installs it (idempotent). macOS re-runs take effect immediately; on Windows re-run install.ps1 from an elevated PowerShell with the same $env:CODECOMBO_* values as the original install. 现行 install.sh 会同装 polkit 放行规则让应用能自重启服务；早期脚本 装的实例没赶上这条规则、自重启被拒——重跑一次安装脚本即补装（幂等）。macOS 重跑立即 生效；Windows 在管理员 PowerShell 里按原安装的 $env:CODECOMBO_* 值重跑 install.ps1。

Lock & remote access锁与远程访问

What actually protects the workbench?工作台到底靠什么保护？

The lock password set on first start gates the whole UI, API and terminal surface — one gate, not per-feature passwords. Auto-lock (idle timeout) and session-token TTL are configurable in Settings → Security; security-relevant events (LAN password setup, unlocks, high-risk approvals) land in the audit log. By default the server binds 127.0.0.1 only — opening it to the network is an explicit act (-H 0.0.0.0), and TLS is on by default when you do. 首启设置的锁密码把 UI、API 与终端面整体关在门后——一道门，而非 每个功能各设一密。自动锁定（空闲超时）与会话令牌 TTL 在 设置 → 安全 里可配； 安全相关事件（局域网设密、解锁、高危审批）落审计日志。服务默认只绑 127.0.0.1——对网络开放是显式动作（-H 0.0.0.0），开放时 TLS 默认开启。

Password setup answers 403 “only allowed from localhost”设密返回 403「only allowed from localhost」

By design: first-time setup is a credential-claiming operation, so a server bound to 127.0.0.1 only accepts it from the machine itself — this prevents someone else on the LAN from claiming the password before you. Headless deployment without a local browser? Restart bound to all interfaces (-H 0.0.0.0) and the setup can be completed from another machine — the action is audited. 这是设计如此：首次设密属于凭证占位操作，服务绑 127.0.0.1 时只接受本机来源——防止局域网里别人抢在你之前占住密码。无头部署没有本机浏览器？ 以通配地址重启（-H 0.0.0.0）即可从另一台机器完成设密——该操作会入 审计日志。

Unlock or setup answers 429解锁或设密返回 429

Same-IP rate limiting on the credential endpoints — wait 60 seconds and retry. 凭证端点的同 IP 限流——等 60 秒再试。

The browser warns about the TLS certificate on first visit首次访问浏览器提示 TLS 证书警告

TLS is on by default with a self-signed certificate — trust it once per client, or install a CA-signed certificate in Settings → Security → TLS (the docs cover both per platform). Reverse-proxying through a VPS? Mind the trust boundary: whoever terminates TLS sees the plaintext. TLS 默认开启、配的是自签证书——每个客户端信任一次即可，或在 设置 → 安全 → TLS 里装入 CA 签发证书（文档按平台各有步骤）。经 VPS 反代？注意信任 边界：终结 TLS 的一方看得到明文。

Forgot the lock password忘记锁密码
codecombo reset-lock# local CLI — resets the lock config; data untouched# 本机 CLI——重置锁配置；数据不受影响

Runs on the machine itself (it must — that's the point: remote callers can't reset a lock they can't touch). 只能在机器本机执行（必须如此——远程来的调用方本就不该能重置自己 碰不到的锁）。

Settings / share dialogs / lock screen flicker over remote control远程控制时设置、分享弹窗或锁屏一直闪烁

The overlays are full-screen frosted-glass layers whose blur is re-sampled every frame; over a remote-control stream (UU, Remote Desktop, TeamViewer, screen sharing) that re-composition can surface as whole-panel flicker, while the same machine is fine when used locally. Two mitigations ship by default: modal masks and glass panels no longer blur (no visible difference — the panels already had opaque backgrounds), and the lock screen keeps its frosted privacy backdrop unless you opt into the reduced tier. Turn on Settings → Appearance → Visual effects: Reduced (or open /?__lowfx=1 once) to drop the remaining blur, make overlays opaque and stop decorative animations — loading spinners keep running. It is a per-device preference and does not roam with your account. 这些弹层是全屏磨砂玻璃层，模糊每帧重采样；经远程控制（UU、 远程桌面、TeamViewer、屏幕共享）串流时，这种整体重新合成会表现为整块闪烁，而同一台 机器本地操作正常。默认已降级两处：弹窗遮罩与玻璃面板不再模糊（观感无差——面板本就 带不透明底色），锁屏默认仍保留防窥磨砂背景。把 设置 → 外观 → 视觉特效 切到 「减弱」（或打开一次 /?__lowfx=1）即去掉剩余模糊、遮罩改实底并停用装 饰性动画——加载 spinner 等必要反馈保留。该偏好按设备本地生效，不随账号漫游。

If flicker persists with the reduced tier on, it is on the capture/compositing side (remote-control encoder or software rendering), not in the page: try turning off hardware acceleration in the remote-control app or in the browser, and record the details below when reporting. 若减弱档下仍闪，则在捕获/合成侧（远程控制编码器或软件渲染）， 不在页面本身：可试关闭远程控制软件或浏览器的硬件加速，并按下述模板记录后反馈。

Diagnostic template (about two minutes): remote-control app and version + capture/encode profile; Chrome version; chrome://gpu summary and the WebGL renderer (SwiftShader means software compositing); remote resolution; per surface (settings / share dialog / lock screen) whether flicker is gone, reduced or unchanged; a screenshot or short recording. Add ?__debug-flicker=1 to the URL and copy the [flicker] console lines (they now include the sampled backdrop-filter / background and an env line with the low-effects state, WebGL renderer and frame-interval p50/p95). 诊断模板（约两分钟）：远程控制软件名与版本 + 捕获/编码档位；Chrome 版本；chrome://gpu 摘要与 WebGL renderer（出现 SwiftShader 即软件合成）；远端分辨率；三个面（设置 / 分享弹窗 / 锁屏）各自「消失 / 减轻 / 不变」 的结论；截图或录屏。URL 加 ?__debug-flicker=1 并复制 [flicker] 控制台行（现含采样的 backdrop-filter / 底色，以及低特效状态、WebGL 渲染器、帧间隔 p50/p95 的 env 行）。

Common errors常见报错

systemctl status: status=203/EXEC, the service keeps failing to restart服务反复重启失败

systemd cannot execute the binary at ExecStart. Read the actual reason first: journalctl -u codecombo -n 30 --no-pager → the line “Failed to execute”, then match one of three states: systemd 执行不了 ExecStart 指向的二进制。先看具体原因： journalctl -u codecombo -n 30 --no-pager → 找 “Failed to execute” 行， 按三态对号：

Error after “Failed to execute”报错 Meaning & fix含义与处置
Permission denied Missing exec bit (chmod 0755 <bin>), an SELinux label on a fresh file (restorecon -v <bin>), or the binary sits on a noexec mount. 缺执行位（chmod 0755 <bin>）、新文件 SELinux 标签不对（restorecon -v <bin>），或二进制在 noexec 挂载点上。

No such file or directory The ExecStart path is wrong — compare systemctl cat codecombo with ls -l. The release binaries are statically linked, so a missing library would not produce this — suspect the path first. ExecStart 路径不对——拿 systemctl cat codecombo 对照 ls -l。发布二进制是静态链接，缺动态库不会报这个错——优先怀疑 路径。
Text file busy when replacing the binary：换二进制时报这个错

The service is still running and you overwrote the executable in place (cp/dd do that). Stop the service first (systemctl stop codecombo, or codecombo stop for manually started instances). Renaming with mv doesn't trigger this — the in-app updater and the manual recipe both swap via rename for exactly this reason. 服务还在跑、而你在原地覆写了可执行文件（cp/dd 就是这种）。先停服务（systemctl stop codecombo，手动启动的实例用 codecombo stop）。mv 改名不会触发——应用内自更新与手工换包 配方都用 rename 正是为此。

A share link opens 404分享链接打开是 404

Default share links ride the main app origin (/s/<token>) — whatever entry the link uses must forward /s/* (plus the three vendored visitor assets). A reverse proxy that only forwards the main port's static pages is not enough; forward the whole main port (SSE live terminals need buffering off). Links pinned to a dedicated share domain must reach the share sub-service port. 默认分享链接走主应用 origin（/s/<token>）——链接 从哪个入口进，该入口就必须转发 /s/*（外加三个访客静态资产）。只转发主 端口静态页的反代不够；要完整转发主端口（SSE 终端直播需关缓冲）。指到专用分享域名的 链接则必须能到达分享子服务端口。

How does a visitor send a file into a writable shared terminal — and which browsers work?访客怎么把文件送进可写分享终端？哪些浏览器能用？

The writable page carries a persistent Upload files/images button that works in every browser and on mobile — images are compressed, the same type and size limits apply, and the saved path is typed into the terminal. With the terminal focused, Ctrl+V is handled by the page (native browser paste is allowed through): files upload as above and plain text is pasted through the terminal input channel — Ctrl+V is no longer forwarded to the host as a literal ^V. Pasting files with Ctrl+V still depends on the browser: Firefox does not populate clipboardData.files when files are copied from the file manager, pasting files is not available in iOS Safari, Safari on the desktop greys the option out, and Android Chrome depends on clipboard permissions. When the clipboard really holds an image the page also tries an explicit clipboard read as a fallback. On mobile or any other browser you can additionally use the collaboration-material entry (camera / choose files — available when the share owner has enabled collaboration); dropping files onto a writable page does not upload anything — the page blocks the default navigation and points you to the upload button or Ctrl+V. 可写页常驻「上传文件/图片」按钮——全浏览器与移动端可用： 图片压缩、类型与大小白名单同链，落盘后把路径键入终端。点击终端聚焦后 Ctrl+V 由页面放行浏览器原生粘贴：文件走上上传链，纯文本经终端输入 通道写入——Ctrl+V 不再作为字面 ^V 转发给主机。Ctrl+V 送文件仍取决于浏览器：Firefox 从文件管理器复制文件不会填充 clipboardData.files，iOS Safari 无法粘贴文件，桌面 Safari 灰显， Android Chrome 受剪贴板权限影响；剪贴板里确有图片时页面还会额外尝试一次显式 剪贴板读取作兜底。移动端或其余浏览器另可在分享者已开启协作时使用协作素材入口 （拍照 / 选择文件）；可写页上的拖拽不会上传任何文件——页面会拦截缺省导航并 提示改用上传按钮或 Ctrl+V。 Upload limits differ by context: local terminal 100 MB (images 20 MB), share visitors and remote terminals 20 MB (images 10 MB) — over-limit errors state the readable "exceeds X MB (current Y MB)" instead of raw byte counts. 上传限额分端：本机终端 100 MB（图片 20 MB）、 分享访客与远程终端 20 MB（图片 10 MB）——超限错误直接给出可读的 「超过 X MB（当前 Y MB）」，不再只报字节数。

Some images in a shared Word document show as placeholders分享的 Word 文档里部分图片显示为占位块

The in-browser preview renders a Word (.docx) document's text layout and loads its embedded images from a same-origin endpoint as the page renders — photos no longer compete for a tiny preview budget, so image-heavy documents render in full. References that cannot be resolved — missing from the file, escaping the package, or not an image relationship — degrade to a placeholder showing the file name and a hint; media the endpoint refuses (over the per-image size cap or not real picture bytes) simply does not load. Neither breaks the page, and the download always contains the original document with every image. Embedded objects (attachments, e.g. files pasted into Word) appear as 📎 blocks carrying the original file name recovered from the document — including Chinese Windows documents whose names are stored in the legacy ANSI (GBK) encoding, which are decoded back to readable text. Previewable types (HTML/PDF/images/plain text/Markdown) get a preview action that opens in a new tab so the reading column stays clean: HTML prototypes open in a dedicated previewer page — title, a scripts risk-ack checkbox plus an optional forms-and-popups switch applied via a plain form resubmit (no JavaScript), and a full-height sandboxed iframe. Embedded text bodies are first extracted out of OLE containers and transcoded to UTF-8 (UTF-16/GBK legacy text stops rendering as mojibake; this extraction is the actual mojibake fix — encoding normalization only hardens the text family). Extraction locates the body by scanning for the declared-length field, so real-world Word writers that store extra header fields are handled, with content anchors as a second line of defense; containers that yield no extractable body open an explicit "this attachment's structure can't be auto-previewed yet — download it to view" page instead of silently triggering a download. Everything stays sandboxed, so prototypes can never read this app's sessions, and neither allow-same-origin nor top-level navigation is ever granted. Anything outside the preview whitelist keeps the plain download. Images stored as EMF/WMF metafiles, which browsers cannot render (a common Windows paste artifact), show an honest placeholder instead of a broken image. 浏览器内预览渲染 Word（.docx）文档的文本排版， 并从同源端点按需加载其内嵌图片——照片不再挤占很小的预览预算，图片型文档也能整份 渲染。无法解析的引用——文件里缺失、越出包外或不是图片关系——降级为占位块 （文件名+提示语）；端点拒收的媒体（超单图上限或不是真实图片字节）则不加载。 两者都不影响整页预览；下载拿到的始终是含全部图片的原始文档。嵌入对象（附件， 例如粘贴进 Word 的文件）在预览中以单行 📎 块呈现，块上带有从文档中还原的原始文件名 ——中文 Windows 时代以 ANSI（GBK）编码存放的名字也会解码还原成可读文本。可预览 类型（HTML/PDF/图片/纯文本/Markdown）获得「预览」动作、新标签打开，阅读列保持 干净：HTML 原型进专门的预览器壳页——标题、脚本风险确认勾选与可选的「允许表单 与弹窗」开关（普通表单重提交生效，零 JavaScript）、全幅沙箱 iframe。嵌入的文本 正文先从 OLE 容器里抽取出来并转码 UTF-8（UTF-16/GBK 老文本不再乱码；乱码 根除靠正文抽取，编码规范化只是文本族供给的健壮性补强）。抽取按扫描式定位数据 长度字段，真实 Word 写入器多出的头字段变体也能抽全，内容锚点回退兜底第二道； 抽不出正文的容器会打开显性提示页「该附件结构暂不支持自动预览，可下载查看」， 不再静默弹下载框——一切都在沙箱内，原型读不到本应用登录态，任何组合都不授予 allow-same-origin 与顶层导航；白名单外的 类型维持纯下载。以 EMF/WMF 图元格式存储、浏览器无法渲染的图片（Windows 粘贴 图的常见产物）则显示诚实占位块，不再破图。

Why does a shared Excel or PowerPoint file open as just an info card?分享的 Excel/PPT 等文件打开只有一张信息卡？

In-browser preview currently covers Markdown, Word (.docx) with loaded images, tabular data (.csv/.tsv/.xlsx), PDF, HTML, images, audio/video and plain text/code. Formats without a preview renderer yet — legacy office files (.xls/.ppt/.pptx), OpenDocument (.odt/.ods/.odp), .epub, fonts — are known formats, so the share page says so explicitly: “preview is not available for this format, you can download it instead”, along with the file's name, size and modification time. Unrecognized extensions show the same info card without that note. Either way, downloading always delivers the original file. 浏览器内预览目前覆盖 Markdown、Word（.docx）与 加载内嵌图片、表格（.csv/.tsv/.xlsx）、PDF、 HTML、图片、音视频与纯文本/代码。暂无预览渲染的格式——老办公格式 （.xls/.ppt/.pptx）、OpenDocument （.odt/.ods/.odp）、.epub 与字体——都是已知格式，分享页会显性提示「该格式暂不支持在线预览，可下载后查看」， 并附文件名/大小/修改时间；未识别的后缀则给同一张信息卡但不带这句提示。 无论哪种，下载拿到的都是原始文件。

Typical on remote-deploy layouts after someone re-ran the install script: the templated unit overwrote the deployer's Environment=PATH, so user-level agent installs are no longer on the service's PATH. Restore the unit (re-deploy from the central instance) or re-add the PATH line — see the upgrade table above for the no-script rule. 典型场景：远程部署布局被人重跑了安装脚本——模板 unit 覆写掉了部署器 下发的 Environment=PATH，服务 PATH 里不再有用户级安装的智能体。恢复 unit （从中心实例重新远程部署）或补回 PATH 行——禁跑脚本的规矩见上方升级判别表。

The downloaded “binary” is only tens of bytes下载下来的「二进制」只有几十字节

You grabbed a .sha256/.sig sidecar instead of the binary — the most common wrong-asset pick on the Releases page. Binaries are ~50 MB; re-download and verify with sha256sum -c --ignore-missing SHA256SUMS.txt (must print OK). 拿到的是 .sha256/.sig 伴随小文件而非二进制 ——Releases 页上最高发的「资产拿错」。二进制约 50MB；重新下载并用 sha256sum -c --ignore-missing SHA256SUMS.txt 校验（须见 OK）。

Install fails — “connection reset”, or the download never completes安装失败——连接重置，或下载怎么都下不完

On CN networks the one-liner's source (raw.githubusercontent.com) and GitHub Releases are routinely unreachable or reset mid-transfer. Two fallbacks, most-trusted first: the npm channel (npm i -g codecombo@next — the registry has integrity mechanisms built in), or the same install command through a mirror prefix: CN 网络到一键命令的源（raw.githubusercontent.com） 与 GitHub Releases 常态性不可达或传输中途被重置。两条回退路，按可信度排序：npm 渠道 （npm i -g codecombo@next——registry 自带完整性机制），或走镜像前缀的 同款安装命令：

p=$(mktemp) && curl -fsSL --retry 3 https://ghproxy.net/https://raw.githubusercontent.com/wtr20211202/codecombo/main/scripts/install.sh -o "$p" && sh "$p"; rm -f "$p"# mirror fallback — Linux / macOS# 镜像回退——Linux / macOS

Trust boundary, stated plainly: the sentinel check + SHA256 verification protect against truncated or corrupted transfers — not against a malicious mirror rewriting the content (an altered script that keeps the trailing sentinel still passes; when the SHA256SUMS manifest travels through the same mirror as the binary, the verification baseline can be swapped along with them). For integrity-sensitive setups prefer the official direct link or npm. The Windows one-liner (install.ps1) has no mirror variant documented yet. 信任边界如实说：哨兵自检 + SHA256 校验防的是传输截断/损坏——不防 镜像恶意改写内容（正文被改但保留尾部哨兵仍可通过校验；SHA256SUMS 清单与 二进制同走镜像时，校验基准可被一并调包）。完整性敏感场景首选官方直连或 npm。 Windows 一键命令（install.ps1）暂无对等镜像形态。
